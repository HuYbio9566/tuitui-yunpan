# 老板看得懂的项目整理与 Obsidian 同步规范

> 这份说明可以复制给其他项目，交给 AI 或项目助理执行。
> 核心目标：让非编程专业、只有初中文化的老板，打开项目后能马上看懂“项目是什么、现在做到哪、接下来要做什么”。

## 先告诉你：以后复制哪一份

以后整理其他项目时，直接复制本文件的**全部内容**，不要只复制某一个章节。

本文件已经包含完整方法：项目文件夹怎么分、老板入口怎么写、项目管理材料怎么放、英文代码怎么收好、HTML 页面怎么给老板查看、本地预览怎么一键打开、Obsidian 怎么用软连接查看同一份文件，以及完成后如何检查。

复制时请从标题 `# 老板看得懂的项目整理与 Obsidian 同步规范` 开始，一直复制到本文最后。不要复制当前项目的具体路径、项目名称、版本号和日期；这些内容要由新项目替换。

## 一、总原则

1. 先照顾老板阅读，不先照顾程序员习惯。
2. 项目管理材料和网站代码必须分开。
3. 复杂英文文件可以保留给电脑，但不能让老板一打开就面对它们。
4. 文件只保留一份；需要在不同软件查看时，使用软连接，不复制。
5. Codex 和 Obsidian 的项目文件夹结构必须保持一致，不维护两套不同目录。
6. 不擅自删除历史资料，不擅自发布 GitHub，不擅自改产品范围。
7. 每次整理后都要检查：项目还能打开、GitHub 还能关联、测试没有变坏、Obsidian 能看到中文材料。

## 二、老板打开项目时应该看到什么

项目最外层只放少量、中文、容易理解的内容：

```text
项目名称/
├── 01_老板先看/
├── 02_项目管理/
├── 03_设计资料/
├── 04_历史资料/
├── 05_网站程序（电脑使用）/
├── README.md
├── index.html
└── 网站代码请勿打开.md
```

### 文件夹含义

- `01_老板先看`：只放一份最简单的中文入口。
- `02_项目管理`：放项目总览、当前任务、版本、决策、变更和复盘。
- `03_设计资料`：放页面截图、设计参考和视觉说明。
- `04_历史资料`：放已经结束的旧方案和旧评审。
- `05_网站程序（电脑使用）`：放 HTML、JS、CSS、测试和网站配置。老板不需要打开。
- `README.md`：项目说明书。
- `index.html`：网站演示入口。
- `网站代码请勿打开.md`：告诉非程序员哪些文件不需要看。

## 三、老板入口必须写什么

`01_老板先看/从这里开始.md` 至少回答下面 6 个问题：

1. 这个项目是做什么的？
2. 为谁解决什么问题？
3. 现在做到哪一步？
4. 已经完成了什么？
5. 现在要老板决定什么？
6. 去哪里看演示和项目管理资料？

不要写技术术语。比如不要只写“RAG、OCR、API、CI”，要写成：

```text
系统还没有接入真实文件识别。
现在看到的是可以演示的页面原型。
```

## 四、项目管理区应该固定包含什么

```text
02_项目管理/
├── README.md
├── 项目总览.md
├── 当前任务.md
├── 版本台账.md
├── 变更记录.md
├── 决策日志.md
├── 复盘记录.md
└── 模板/
    ├── 任务模板.md
    ├── 评审模板.md
    ├── 决策模板.md
    └── 复盘模板.md
```

每个文件只做一件事：

- `项目总览`：项目背景、目标用户、当前阶段。
- `当前任务`：现在做什么、谁负责、什么时候完成。
- `版本台账`：产品版本、设计稿编号、代码基线分开记录。
- `变更记录`：项目发生过哪些重要变化。
- `决策日志`：哪些问题已经决定、哪些还在等老板决定。
- `复盘记录`：这次做得好不好、下次怎么改。

## 五、编号必须分开

不能把所有东西都叫“v4”。必须使用不同前缀：

```text
产品版本：1.0.0、2.0.0
设计稿：DESIGN-v1、DESIGN-v2
任务：TASK-20260804-001
评审：REV-20260804-001
决策：DEC-20260804-001
变更：CHG-20260804-001
复盘：RETRO-20260804-001
```

如果还没有正式产品版本，就写“产品版本：未分配”，不要把设计稿编号当产品版本。

## 六、英文代码如何处理

`.html`、`.js`、`.css`、`.test.js` 和 `.git` 不是项目管理材料，而是电脑运行和测试网站需要的文件。

处理方式：

1. 不删除。
2. 不随便改名。
3. 集中放进 `05_网站程序（电脑使用）/`。
4. 在该文件夹内放一份 `说明.md`，告诉老板不要打开。
5. 保留根目录的 `index.html` 作为入口，避免在线演示打不开。

如果网站发布平台要求代码必须在根目录，不要强行移动，优先使用“中文管理区 + 根目录代码”的方案，并用说明文件遮挡复杂内容。

## 七、Obsidian 只查看项目输出材料

### 推荐方式：软连接

软连接的意思是：Obsidian 里看到的是项目原文件的入口，不会复制出第二份文件。

原项目继续放在 Codex/Git 仓库位置，例如：

```text
/Users/用户名/Documents/Codex/项目名称
```

Obsidian 库例如：

```text
/Users/用户名/Documents/Obsidian
```

建议只连接项目管理和输出材料：

```text
Obsidian/项目文件夹/项目名称/
├── 01_老板先看 -> 原项目/01_老板先看
├── 02_项目管理 -> 原项目/02_项目管理
├── 03_设计资料 -> 原项目/03_设计资料
└── 04_历史资料 -> 原项目/04_历史资料
```

Obsidian 和 Codex 必须保持同样的顶层结构。老板可点击的入口直接放在原项目的 `01_老板先看`，不要再在 Obsidian 另建一个 HTML 专用目录或分享目录。`.git` 和部署配置可以留在项目根目录供电脑使用，但不需要建立给老板看的额外副本。

### 建立软连接前必须检查

1. 先确认 Obsidian 库真实路径，不能凭猜测。
2. 先确认目标文件夹不存在，避免覆盖用户已有资料。
3. 如果目标已经存在，先停下来让老板确认。
4. 建立后检查软连接指向的原路径。
5. 随机打开同一个 Markdown 文件，确认 Codex 和 Obsidian 看到的是同一份。

### 不要做的事

- 不要把项目完整复制一份到 Obsidian。
- 不要在 Obsidian 里重新建立一套同名文档。
- 不要把 GitHub 仓库直接当作 Obsidian 库。
- 不要把代码、依赖和部署配置塞进老板的项目管理目录。
- 不要在 Obsidian 另建一套不同于 Codex 的项目目录。
- 不要为了“好看”复制 HTML、Markdown 或截图。

### 网站项目的 HTML 查看和预览

如果项目包含网站页面，可以在 Obsidian 中单独建立：

```text
05_网页页面（HTML）/
└── 老板分享入口_阶段_日期/
    ├── 项目名称_阶段_日期_页面名称.html
    ├── 说明_请先看.md
    └── 老板一键打开本地预览.command
```

HTML 文件使用软连接，不复制原文件。给老板看的 HTML 文件名必须写清项目名称、阶段、日期和页面名称，例如：

```text
推推-云盘工具调研_原型版_2026-08-04_多文件问答.html
```

如果要看到完整网页效果，应提供本地预览服务，而不是只依赖 `file://` 文件地址，因为网页可能依赖 CSS、JS 和其他资源。推荐提供一个 `老板一键打开本地预览.command`，自动启动服务并打开浏览器。常用本地地址：

```text
http://127.0.0.1:8765/index.html
```

手动启动命令：

```bash
cd "/Users/用户名/Documents/Codex/项目名称/05_网站程序（电脑使用）"
python3 -m http.server 8765 --bind 127.0.0.1
```

老板分享入口的说明必须写清：项目阶段、产品版本、日期、推荐点击顺序、本地预览方法、预览地址，以及当前是原型还是正式产品。

## 八、GitHub 和 Codex 关联检查

整理目录后必须检查：

```text
本地项目根目录 = 真的包含 .git 的目录
远程仓库 = 目标 GitHub 仓库
分支 = main 或团队约定的主分支
工作树 = 没有意外修改
```

项目名、Codex 项目名和 Obsidian 文件夹名最好保持一致，例如：

```text
推推 - 云盘工具调研
```

GitHub 仓库名可以不同，但必须在项目说明里写清楚链接。

## 九、完成后必须验收

整理完成后，逐项检查：

- 老板打开项目最外层，是否首先看到中文目录。
- `01_老板先看/从这里开始.md` 是否能看懂。
- `02_项目管理/项目总览.md` 是否写明当前阶段。
- `当前任务.md` 是否列出需要老板决定的问题。
- 根目录 `index.html` 是否还能打开网站。
- JavaScript 语法检查是否通过。
- 自动测试是否通过。
- GitHub 远程地址是否仍然正确。
- Obsidian 是否能看到中文项目材料。
- Obsidian 里的文件是否为软连接，而不是复制品。
- Obsidian 是否能看到 HTML 页面入口。
- HTML 文件名是否包含项目名称、阶段和日期。
- 一键预览文件是否能启动本地服务并打开工具中心。
- 本地预览地址是否能访问首页和至少一个核心页面。

## 十、给 AI 的执行要求

把这份说明交给 AI 时，附加以下要求：

```text
请先只读检查，不要马上改文件。
先报告当前项目根目录、Git 状态、远程地址、发布入口和 Obsidian 库路径。
任何删除、移动、复制、归档或建立软连接前，先说明会影响什么。
不要复制出第二份项目。
不要把代码文件改成中文名。
不要删除 .git、部署配置和测试文件。
整理目标是让非编程专业老板打开项目就能看懂。
完成后运行语法检查和测试，并报告结果。
涉及 GitHub push、tag、Release、Pages 发布时，必须单独请求确认。
```

## 十一、最终判断标准

如果老板打开项目后，能在 30 秒内回答“这是什么、做到哪、接下来要决定什么”，说明整理合格。

如果老板仍然需要打开 `.js`、`.css`、`.git` 或询问程序目录是什么意思，说明项目管理区还没有整理好。
